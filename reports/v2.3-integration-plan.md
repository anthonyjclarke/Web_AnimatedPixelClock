# ESP32 v2.3 integration plan

Reviewed 10 September 2026 against `../AnimatedPixelClock` and `release/v2.3.0/CHANGELOG.md`.

This is a review and implementation plan. No animation code, firmware, companion configuration or deployment was changed. Installation directions in the changelog were treated as release documentation, not instructions to flash hardware.

## Findings and limits

- The new effects are **audio visualizers**, not additional clock styles: Starfield Overdrive (firmware visualizer ID 5) and Oscilloscope (ID 6). The web project currently has no audio input, visualizer mode, companion transport, weather screen, network settings or PC statistics integration.
- The updated source folder has no Git history. Its current implementation is the reference, but an exact v2.2-to-v2.3 diff cannot be established from this folder alone. The release changelog does not list Mario or Pac-Man fixes.
- The user's Pac-Man and Mario fidelity reports remain unresolved. Previous unit and mocked-drawing checks did not establish pixel or motion parity. Their passing results must not be used to dismiss the observed problems.
- Current Pac-Man does contain digit paths, an eaten mask and deferred replacement. Therefore “eating is absent” is not established for the current local source. First establish which build is actually visible, then reproduce the visible failure. The updated local ports have not been published; a hosted copy can still show older loops.
- The web renderer approximates firmware circle/triangle rasterization and draws through an LED-spacing layer. Compare its native 128×64 framebuffer before glow/scaling; only then compare presentation. The tests currently assert `eaten.size > 5`, rather than verifying all lit pellets and their rendered disappearance.
- Mario currently ports only the firmware defaults: two-frame sprite, walking/jumping digit hits and idle off-screen. The firmware contains optional enemy, coin, star, mushroom and multi-enemy encounters, disabled by default. A configured hardware clock can therefore look very different. Verify the intended settings and scene before extending that scope.

## Phase 1 — reproduce and correct Pac-Man and Mario

1. Establish a reproducible preview of the current checkout, with a visible build identifier in development. Capture the problematic sequence in the actual browser. Confirm playback is running, active style and settings, and that the shown assets belong to this checkout.
2. Build a deterministic reference harness around the current firmware implementations using a mock display, controllable `millis()`, time, settings and random seed. Preserve the source algorithms; capture native frames and state events. Start with the drawing and transition functions, expanding the C++ shim only as needed.
3. Compare browser native frames and event timelines with firmware at identical times/settings. Cover normal patrol, second 56, a one-digit change, 12:59→13:00, noon/midnight in both hour formats, replay, pause/resume and switching away/back.
4. Pac-Man: verify each lit glyph pellet stays visible until consumed, becomes absent in the framebuffer, and stays absent until replacement. Check patrol pellet consumption/regeneration, original 5px spacing and radius-1 circles, radius-7 proximity eating, all ten ordered paths, directional mouth/eye drawing, returning to y=56, and replacement/bounce only after returning. Fix a reproduced discrepancy rather than inventing a replacement animation.
5. Mario: verify original GFX glyphs, digit x positions/y=26, 16ms timing with the 16/35 motion scale, original sprite/color pixels, target center, head collision and immediate digit update, bounce, landing and exit. Compare walk-frame cadence and rounding. Add the relevant optional encounter configuration only after determining that it is part of the desired hardware behavior.
6. Acceptance: native-frame differences are explained or eliminated; character contacts match visible changes; browser recordings show correct behavior over several minute transitions. State-machine tests remain useful, but are not the visual acceptance gate.

Relevant source: `src/clocks/clock_pacman.cpp` (target/eat/return: 309–450, paths/proximity: 479–584, pellets/sprite: 697–790); `clock_mario.cpp` (transition and sprite: 244–444, encounters later in file); `clock_common.cpp` (bounce/time override); `src/config/settings.cpp` (default settings).

## Phase 2 — shared rendering and time handling

Use one native-resolution framebuffer, shared firmware-compatible drawing primitives, a complete frame per presentation, and separate simulation time from wall-clock time. Preserve state across appearance changes and pause; reset deliberately on replay, style or source changes. Keep a valid cached time value for corner-clock rendering rather than clearing it during transient data unavailability.

The ESP32 blank-frame fix includes DMA scan synchronization and skipping a redundant clear for fully repainting custom animations (`src/main.cpp:373–384`). Those hardware calls do not belong in the browser. Apply the equivalent complete-frame rendering principle and test for blank frames. `ambient/ambient.cpp` and `viz/visualizer.cpp` use `peekLocalTime()` for nonblocking corner-clock reads.

## Phase 3 — audio input contract and visualizer mode

Create a visualizer mode separate from clock styles, with effect and color controls in separate cards, following the v2.3 settings organization. Keep native firmware effect IDs stable; do not treat array indices as IDs (ID 4 is not one of the current listed effects).

Define an audio frame containing 32 unsigned amplitude bands, optional 128 waveform bytes centered on 128, packet serial and receive timestamp. The firmware accepts `FFT1` + 32 bytes (36 total), optionally followed by 128 waveform bytes (164 total). A legacy packet must invalidate an earlier waveform. Audio becomes stale after 2 seconds; the visualizer's mode eligibility/grace window is 10 seconds.

Recommended first input: browser-selected audio file, plus microphone where available, producing the same normalized frame contract. Implement waveform trigger alignment and gain behavior from the companion rather than drawing an unrelated sine wave. Provide a clearly labelled deterministic demo source for testing only.

If matching the PC's system audio is required, plan a local companion-to-browser adapter (for example a WebSocket endpoint). The existing UDP protocol cannot simply be passed to the browser renderer. Define connection, permissions, secure/local deployment compatibility and reconnection behavior before selecting the transport. Do not equate microphone capture with PC system-audio capture.

Source: `src/viz/visualizer.h:14–36`, `visualizer.cpp:148–181,211–269`; companion `companion-common/audio_spectrum.py:374–417` (decimation, rising zero-crossing alignment, gain, packet payload).

## Phase 4 — port the two new effects

### Oscilloscope

Port `src/viz/oscilloscope.cpp`: 128-point live trace, original graticule, deflection color gradient, optional center fill, flat color option, gain 50–200%, and 0–4 ghost traces. History advances only when the waveform serial changes, not once per display refresh. Match geometry with/without the 10px clock band. Clear stale history on reset, missing waveform or stale data. Translate the firmware's companion-update message into an input-specific message when using browser-native audio.

Acceptance: known flat/ramp/sine/clipped input vectors produce expected pixels; duplicate serials do not duplicate trails; legacy frames, disconnect and source switching do not leave a stale waveform; gain and all trail depths work.

### Starfield Overdrive

Port `src/viz/starfield.cpp`: 96 persistent 3D stars, perspective projection/respawn, bass-driven speed, midrange center drift, band-colored tips and persistent radial trails. Hyperspace bursts derive from packet-to-packet bass spectral flux with cooldown and stream-gap rebaselining. A held loud tone must not repeatedly trigger a burst.

Acceptance: seeded stars match reference trajectories; silence, sustained tone, isolated beat, repeated beats and stream gaps produce the expected speed, trail and burst response. Rendering the same audio at 30/60/120Hz must not multiply beat triggers. Verify no blank frames during effect/clock-overlay changes.

## Delivery order and scope

1. Resolve Pac-Man and Mario against native reference frames and browser playback.
2. Consolidate rendering/time behavior and regression fixtures.
3. Add audio input and separate visualizer controls.
4. Integrate Oscilloscope, then Starfield Overdrive, with signal-driven acceptance tests.
5. Keep weather, ambient library, device NTP and PC management as explicitly scoped follow-on features.

No source upload or publishing is part of this plan. Publishing remains a separate step requiring the previously requested authorization.
